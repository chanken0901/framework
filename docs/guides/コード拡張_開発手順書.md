# FrameWork コード拡張・開発手順書

更新：2026-10-21。対象：ローカルにクローンしたFrameWorkを自分で拡張する学生・開発者。
実際のファイル配置と入力経路に基づく。数値アルゴリズムの正しさや本番条件の妥当性は、別途検証する。

## 1. 最初に押さえること

**FrameWorkが開発の正本、ResearchRuns等は生成した計算環境である。**
生成環境のソースだけを修正しても、FrameWorkや次に作る環境には反映されない。
原則として正本を修正し、別の検証用環境を生成して試す。実行中の環境は上書きしない。

- 既存機能の既定値・入出力・無次元化を無断で変更しない。
- 任意拡張は無効時に既存経路へ戻る設計とし、そのことをテストする。
- 未対応の組合せは入力時に明示的に拒否し、黙って無視・別方式へ変更しない。
- 計算本体は既存Fortran構成に合わせる。現在のCUDAカーネルはCUDA C++、運用・入力生成はPythonである。
- 「ビルドできた」「短時間動いた」「物理的に検証した」は分けて報告する。

最短の流れ：

```text
仕様・対象範囲を決める → 作業ブランチ → CPUの最小実装
→ YAML/入力/manifestを接続 → 単体試験 → MPI/OpenMP/CUDA対応
→ 新規生成環境で試験 → 仕様書更新 → コミット・PR
```

## 2. 変更するライブラリを選ぶ

| 目的 | 正本と案内 |
|---|---|
| 単成分圧縮性流れ・熱揺らぎ | [NSE](../../SolverLibrary/NSE/README.md) |
| GPE・量子流体 | [GPE/GP3D](../../SolverLibrary/GPE/gp3d/README.md) |
| 詳細反応機構・新規反応流 | [ReactingFlow](../../SolverLibrary/ReactingFlow/README.md) |
| 既存Stage系列の保守・比較 | [旧NSE多成分系列](../../SolverLibrary/NSE/docs/legacy-multicomponent/NSE_MULTICOMPONENT_ROADMAP.md) |

別物であり、R番号とStage番号も一致しない。ReactingFlowはR4が未完了である。

## 3. 作業開始と仕様メモ

まずGitの状態を確認する。未コミット変更があれば内容を把握し、必要なものを別コミットにする。
`reset --hard`や一括削除で作業を消して整理しない。

Windows / PowerShell（実際のクローン先へ変更）：

```powershell
cd C:\Users\Owner\Documents\Codex\FrameWork
git status --short
git branch --show-current
git switch -c feature/my-extension
```

Linux / bash（以下はホーム直下へクローンした例）：

```bash
cd "$HOME/FrameWork"
git status --short
git branch --show-current
git switch -c feature/my-extension
```

`feature/my-extension`は追加内容を表す名前に変更する。同名ブランチが既にある場合は
新規作成せず、そのブランチで作業を続けるか判断する。既存変更がある状態で安易にmainへ切り替えない。

実装前に次を短く書き出す：

1. 追加する方程式・モデル・離散式、単位／無次元基準。
2. 新しい設定名、既定値、許容範囲。省略した既存入力の振る舞い。
3. 対象：等間隔／不等間隔、境界、CPU／MPI／OpenMP／CUDA。
4. ghost幅、追加メモリ、追加通信、時間刻み制約。
5. 保存則・正値性・再スタートに及ぼす影響。
6. 合格条件：比較対象、格子・dt、誤差指標、許容誤差。

## 4. NSE：変更箇所を探す

| 追加内容 | 主な場所 |
|---|---|
| 物理設定の保持 | `SolverLibrary/NSE/src/common/mod_model_config.f90`の`nse_config` |
| 共通の格子・時刻等 | `src/common/mod_common_config.f90`の`simulation_config` |
| input.dat読込み | `src/io/mod_input_reader.f90` |
| 初期条件 | `src/init/`と`mod_nse_initial_conditions.f90`の選択処理 |
| 境界条件 | `src/boundary/mod_boundary_runtime.f90`、対応する個別モジュール |
| 対流方式 | `src/numerics/convective/`のdispatch・leaf registry・個別流束 |
| 再構築／Riemann解法 | `src/numerics/reconstruction/`、`src/numerics/riemann/` |
| 粘性・熱伝導 | `src/numerics/viscous/` |
| RHSの接続 | `src/numerics/mod_nse_spatial_operator.f90` |
| 時間積分 | `src/time/mod_nse_time_integration.f90` |
| 任意の物理拡張 | `src/extensions/`。揺らぎの例は`fluctuating/` |
| CUDA | `src/gpu/mod_nse_gpu_cuda.f90`、`nse_cuda_bridge.cu`、関連`.cuh` |
| MPI＋CUDA交換 | `src/gpu/mod_nse_gpu_mpi.f90` |
| 出力・再開 | `src/io/`と初期化側の再スタート処理 |

この表の`src/`はNSE直下。詳しくは[モジュール設計](../../SolverLibrary/NSE/docs/overview/NSE_MODULE_DESIGN.md)。
mainは呼出しの順序を管理する場所とし、個別の流束式や物理モデルを集中させない。
`common`から特定の流束・mainへ逆向きの依存を作らない。

## 5. YAMLからFortranまで、設定を最後まで接続する

```text
環境設計YAML → テンプレートの選択・生成
case.yaml ＋ 明示参照したconfig/*.yaml
  → case_configuration.py：合成・検査
  → case_input.py：検査・input.dat生成
  → mod_input_reader.f90：namelist読込み
  → nse_config／simulation_config
  → 初期化・境界・RHS・時間積分／CUDA
```

### 5.1 既存モデルにパラメータを追加する

以下を**一組として**確認する。

1. `ScriptLibrary/RunEnvironment/case_templates/`の該当テンプレートに設定・説明を追加。
2. `case_input.py`の該当resolverで型・有限値・範囲・組合せを検査。
3. NSEの出力キー一覧`NSE_KEYS`に必要なnamelist名を登録。resolverが値を返すだけでは出力されない。
4. `nse_config`等にフィールドと既定値を追加。
5. `mod_input_reader.f90`にローカル変数、namelist宣言、読込み前の既定値設定、読込み後のcfgへの代入を追加。
6. Fortran側でも検査。input.datを直接編集して実行する経路を考慮する。
7. 計算箇所で値を使用し、必要な場合は実行ログにも有効値を表示する。

実例：現在の`fh_boundary_model`は、拡張YAMLの`boundary_models`をresolverが6整数へ変換し、
`NSE_KEYS`、namelist、`nse_config`を経由してCPU/CUDAへ渡す。これを追うと経路を確認できる。

### 5.2 新しい任意拡張を作る

以下は**設計例であり、未登録のまま実行できる設定ではない**。

case.yaml：

```yaml
schema_version: 2
extensions:
  my_extension: config/my_extension.yaml
```

config/my_extension.yaml：

```yaml
schema_version: 1
extension: my_extension
config:
  enabled: false
  coefficient: 0.0
```

- `case_configuration.py`の`EXTENSION_TARGETS`へ、拡張名と合成先を登録する。
- 合成先を既存モデルと衝突させず、resolver・キー検査・出力処理を追加する。
- `case_templates/extensions/`に雛形を追加し、必要なケースの生成定義から参照する。
- 新しい選択肢が必要なら`environment_options.yaml`、関連schema、`profile_selection.py`も確認する。
- `case_template_overlay.py`の差分継承を使う場合は通常NSEテンプレートを複製しない。
- enabled=falseと拡張省略の両方をテストする。

詳細：[ケース設定と拡張YAML](../../ScriptLibrary/RunEnvironment/CASE_CONFIGURATION.md)。
`input.dat`や`resolved_case.yaml`を設定の正本にしない。再生成で上書きされる。

## 6. 計算本体を実装する

### 初期条件の追加例

1. `src/init/mod_init_<name>.f90`に既存の初期化APIに合わせた処理を作る。
2. `mod_nse_initial_conditions.f90`の選択処理から呼ぶ。
3. `case_input.py`で`flow.type`と新しいパラメータを解決し、未対応格子を拒否する。
4. 物理セル中心座標を使用する。不等間隔へ`i*dx`を流用しない。
5. ghostをどの段階で埋めるかを既存処理に合わせる。保存変数と原始変数を混同しない。
6. 再スタート分岐が初期条件生成より先に実行されることを維持する。

### 境界・流束・揺らぎを変更する場合

- x/y/zと両端の符号、法線方向、辺・角を検査する。xだけの試験で完成としない。
- MPI分割面と物理境界を区別する。周期は反対側と対になる。
- 必要ghost数を宣言し、割当て・halo交換・GPU領域にも反映する。
- 保存形では共有面の流束を一致させる。格子重みと発散の分母を統一する。
- 不等間隔KEEP6の積分重みは物理セル体積とは限らない。
- 揺らぎは散逸と雑音を一組で変更する。単に乱数を追加・削除してFDT成立としない。
- 揺らぎ有効時のCENTRAL6指定は専用輸送への置換であり、通常の六次精度粘性ではない。
- 密度・圧力の異常を黙って切り詰めない。既存の停止／再試行方針を確認する。
- 再開に必要な状態を増やした場合、保存形式・読込み・互換性・step/seedの継承も検討する。

境界の現在の範囲は[境界仕様](../../SolverLibrary/NSE/docs/numerics/NSE_BOUNDARY_CONDITIONS.md)、
揺らぎは[LLNS仕様](../../SolverLibrary/NSE/docs/physics/NSE_FLUCTUATING_HYDRODYNAMICS.md)を参照。

## 7. CMakeとmanifestの両方へ登録する

新しい`.f90`を置くだけでは、コンパイルも生成環境へのコピーも保証されない。

| 登録先 | 役割 |
|---|---|
| 各ライブラリの`CMakeLists.txt` | コンパイル対象、依存ライブラリ、テスト実行 |
| NSEの`solver_manifest.yaml` | 単成分NSEのprofile別配布ファイル・ビルド設定 |
| NSEの`solver_manifest_multicomponent.yaml` | 旧多成分系列。単成分とは別に扱う |
| GPEの`gp3d/solver_manifest.yaml` | GPEの配布・profile |

1. ソースを適切なCMake targetへ追加する。
2. manifestの該当componentの`files`へ追加し、必要profileからcomponentが参照されることを確認する。
3. テストのソース・入力・補助モジュールも同梱する。テストスクリプトがimportする別ファイルを忘れない。
4. 必要文書はruntime_tools等の文書コピー定義にも登録する。
5. 元リポジトリのビルドに加え、**新規生成環境だけで**入力生成とビルドが通ることを確認する。

profile名やmodel名を増やすのは、依存ライブラリや実行基盤が本当に変わる場合に限る。
単なる実行時パラメータの追加のために専用mainやソースのコピーを量産しない。

## 8. MPI・OpenMP・CUDAへ接続する

CPU版の数式と単体試験を基準に、同じ離散式を各実行構成へ接続する。

- **MPI**：局所添字と全体添字を区別。halo幅、通信順序、全rankのdt・異常判定を確認。
- **OpenMP**：共有作業配列、private変数、初期化、バリアを確認。1/2スレッドで比較。
- **CUDA**：Fortranの`bind(C)`とC側の型・引数順を一致させる。整数、論理値、配列順序に注意。
- GPU常駐配列は初期化時に確保し、各段で不要な全配列のCPU往復や再確保を追加しない。
- `.cuh`を追加したらbridgeへのincludeとmanifestへの登録も確認する。
- **MPI＋CUDA**：局所GPU添字から全体座標を復元。物理境界を内部rank境界へ誤適用しない。
- CUDA-aware直接通信とCPU経由のstaged通信を区別し、実際に使った方式を検証記録に残す。
- 1GPUを複数rankで共有した試験を、複数GPU実機での通信・性能検証と呼ばない。

CPUのみ実装する段階では未対応backendを明示的に拒否する。CUDA版が旧式のまま動く状態を放置しない。

## 9. テストとコマンド

前提：Python、CMake、Ninja、対応FortranコンパイラがPATHから利用できること。
MPI/CUDA/FFTは選択profileに応じて追加する。以下のコマンドは依存ライブラリを自動導入しない。

### 9.1 入力・文書のテスト（FrameWork直下）

Windows：

```powershell
python -B -m unittest discover -s ScriptLibrary/RunEnvironment/tests -p test_case_input.py
python -B -m unittest discover -s ScriptLibrary/RunEnvironment/tests -p test_fluctuating_hydrodynamics.py
python -B -m unittest discover -s ScriptLibrary/RunEnvironment/tests -p test_document_layout.py
```

Linux：

```bash
python3 -B -m unittest discover -s ScriptLibrary/RunEnvironment/tests -p test_case_input.py
python3 -B -m unittest discover -s ScriptLibrary/RunEnvironment/tests -p test_fluctuating_hydrodynamics.py
python3 -B -m unittest discover -s ScriptLibrary/RunEnvironment/tests -p test_document_layout.py
```

変更対象のテストを追加し、環境生成を変更したら`test_prepare_environment.py`も実行する。
失敗は変更前からのものか切り分ける。既存の失敗を無断でスキップしたり、誤差を緩めて通したりしない。

### 9.2 NSEのCPU最小ビルド（両OS共通、FrameWork直下）

以下はGNU Fortranを想定したMPIなしの独立検証用。既存キャッシュを使い回さない。
WindowsではGNU/Ninjaが利用できる端末で実行する。

```text
cmake -S SolverLibrary/NSE -B build/dev-nse-cpu -G Ninja -DCMAKE_BUILD_TYPE=Debug -DNSE_USE_MPI=OFF -DNSE_ENABLE_OPENMP=ON -DNSE_GPU_BACKEND=none -DBUILD_TESTING=ON
cmake --build build/dev-nse-cpu --parallel 4
ctest --test-dir build/dev-nse-cpu --output-on-failure
```

境界外アクセスの調査ではコンパイラの境界検査・backtraceも有効にする。
Debugという名前だけで全ランタイム検査が有効とは限らない。
MPI／CUDA／FFTの構成は[NSEビルド手順](../../SolverLibrary/NSE/docs/usage/NSE_BUILD_AND_RUN.md)と
[共通ビルドランナー](../../ScriptLibrary/BuildSolver/README.md)に従う。
コンパイラやbackendを変える場合は新しいbuildディレクトリを用意する。

### 9.3 生成環境による確認

環境設計書のsourceを自分の正本にし、destinationを新しい検証先へ設定する。
既定のResearchRunsへ不用意に生成しない。設計書を別の場所へコピーした場合は相対パスを再確認する。

Windows（FrameWork直下、例の設計書は先に検証先へ設定しておく）：

```powershell
python ScriptLibrary/RunEnvironment/prepare_environment.py ScriptLibrary/RunEnvironment/environment.nse.yaml --dry-run
python ScriptLibrary/RunEnvironment/prepare_environment.py ScriptLibrary/RunEnvironment/environment.nse.yaml
```

Linux：targetやdestinationをLinux用に設定してから実行する。

```bash
python3 ScriptLibrary/RunEnvironment/prepare_environment.py ScriptLibrary/RunEnvironment/environment.nse.yaml --dry-run
python3 ScriptLibrary/RunEnvironment/prepare_environment.py ScriptLibrary/RunEnvironment/environment.nse.yaml
```

生成ログに表示されたフォルダへ移動し、小さい格子・数ステップ・専用出力先のcase.yamlで確認する。

Windows：

```powershell
python tools/run_case.py --prepare
python tools/run_case.py --validate-only
python tools/run_case.py --build
python tools/run_case.py --test
python tools/run_case.py --run
```

Linux：

```bash
python3 tools/run_case.py --prepare
python3 tools/run_case.py --validate-only
python3 tools/run_case.py --build
python3 tools/run_case.py --test
python3 tools/run_case.py --run
```

`--prepare`は入力再生成であり、正本の最新ソースを既存環境へコピーする操作ではない。
新しいコードを検証するには環境の再生成／管理された更新と再ビルドが必要。

### 9.4 合格判定

| 検査 | 最低限確認する内容 |
|---|---|
| 入力 | 新キーがinput.datに出る、未指定時は旧動作、不正値・未対応組合せは拒否 |
| 局所計算 | 既知解、対称性、保存則、均一場の保持、NaN/負値の扱い |
| 収束 | 格子・dtを変え、誤差と実効次数を確認 |
| 並列一致 | 1rank対複数rank、OpenMP有無、CPU対CUDA、内部境界・辺・角 |
| 再スタート | 連続実行対途中再開、時刻・step・seed、対応範囲内で並列数変更 |
| 無効時 | 拡張なしとenabled=falseで既存結果を維持 |
| 配布 | 新規生成環境で不足ファイルがなく動く |
| 性能 | 追加メモリ・通信・時間、GPU常駐の維持 |

浮動小数点のビット一致を全backendへ強制しない。絶対／相対誤差の根拠を記録する。
揺らぎでは単一実現の一致に加え、複数試行の平均・分散・FDTを確認する。
非周期の開放系に周期系の総量一定をそのまま要求しない。境界流束を含む収支を見る。

## 10. GPEとReactingFlowを拡張する場合

### GPE

`SolverLibrary/GPE/gp3d/src/`の`init`、`solver`、`fft`、`gpu`、`io`等から対象を選ぶ。
`gp3d/CMakeLists.txt`と`gp3d/solver_manifest.yaml`を更新する。
新しい設定は共通のcase入力生成とGPE側の入力読込みの両方へ接続する。
FFTの正規化、実空間／波数空間配置、スラブ／ペンシルの局所形状、転置後の軸順序を検査する。
CPU FFTWとGPU cuFFT/cuFFTMpで同じ初期条件・保存量・時間発展を比較する。
[GP3D README](../../SolverLibrary/GPE/gp3d/README.md)と
[分散GPUテスト計画](../../SolverLibrary/GPE/gp3d/docs/cufftmp_test_plan.md)を参照。

### ReactingFlow

正本は`SolverLibrary/ReactingFlow/src/fortran/`。`mod_rf_thermo`、`mod_rf_kinetics`、
`mod_rf_transport`、`mod_rf_flow1d`／`mod_rf_flow2d`等の責務に合わせる。
専用`CMakeLists.txt`と`tests/`へ登録し、現在の専用実行入口を使用する。
NSEの環境ジェネレーターへ自動接続されると仮定しない。
元素・質量・エネルギー保存、物性の温度範囲、単位、反応速度、剛性積分、境界での反応を検証する。
DVODE依存があり、構成時に取得するか指定revisionのオフラインソースを用意する。
R4の未完了試験を新機能追加で覆い隠さず、[残作業](../../SolverLibrary/ReactingFlow/docs/development/R4_REMAINING.md)と区別して報告する。

## 11. 文書更新とGitへの登録

追加機能の仕様を各ライブラリの内容別docsへ置く。設定例、単位、既定値、対応組合せ、
未対応・未検証、実行コマンド、試験結果を書く。既存README・資料索引からリンクする。
同じ仕様書の旧版コピーを並べず、通常は現行文書を更新し、履歴が必要なものだけ分離する。

FrameWork直下で、以下は両OS共通。山括弧の箇所は実際のパスへ置き換える説明用である。

```text
git status --short
git diff --check
git diff --stat
git add -- <変更したファイルまたはディレクトリ>
git diff --cached --check
git diff --cached --stat
git diff --cached
git commit -m "Describe the implemented extension"
git push -u origin HEAD
```

移動を含む場合は対象を限定した`git add -A -- <対象ディレクトリ>`を使う。
無関係な変更を一括登録しない。build、SLF、計算結果、秘密情報が含まれないか確認する。
GitHubで作業ブランチからmainへのPRを作り、仕様・試験・未対応事項を説明してレビューを受ける。
既存の未コミット変更がある状態でpull、reset、force pushを解決策にしない。
詳細：[Git運用マニュアル](GIT運用マニュアル.md)。

## 12. よくある不具合

| 症状 | 確認すること |
|---|---|
| YAMLを変えても挙動が同じ | resolver、NSE_KEYS、input.dat、cfgへの代入、実際に使う変数 |
| ソース追加後も生成環境にない | manifestのfiles、profileのcomponents、生成元のパス |
| 正本では通るが生成環境では失敗 | テスト入力・import先・`.cuh`・文書等のコピー漏れ |
| CPUは通るがCUDAだけ不一致 | bind(C)、配列順序、global/local添字、ghost、境界・係数の更新漏れ |
| MPI並列数で結果が変わる | 内部面を物理境界扱い、halo不足、乱数にrank番号使用、reduction |
| 再開でstepや乱数列が戻る | 初期条件としての読込みとrestartの混同、step/seed設定 |
| Windows生成時のファイルエラー | 短い検証先でも再現するか、パス長、権限、ファイルロック |
| 新機能無効でも結果が変わる | 既定値変更、共通経路への副作用、輸送方式の暗黙置換 |
